## 1. Подробный разбор метода `BookingService.create`

Файл: `service/BookingService.java`.

```java
@Transactional
public Booking create(Long clientId, Long roomId, LocalDate checkIn,
                      LocalDate checkOut, int guestCount) {
    Client client = clientService.getById(clientId);
    Room room = roomService.getById(roomId);

    Booking booking = new Booking(room, client, checkIn, checkOut, guestCount);

    boolean conflict = bookingRepository
            .findByRoomIdAndStatusIn(roomId, BookingStatus.activeStatuses())
            .stream()
            .anyMatch(existing -> existing.overlaps(checkIn, checkOut));
    if (conflict) {
        throw new RoomNotAvailableException(roomId, checkIn, checkOut);
    }

    Booking saved = bookingRepository.save(booking);
    client.addBooking(saved);
    return saved;
}
```

### Назначение

Главный сценарий: **оформить бронирование номера конкретным клиентом
на выбранные даты**. Метод связывает три сущности (`Client`, `Room`, `Booking`)
и проверяет правила, которые нельзя проверить внутри одной сущности —
например, пересечение с *другими* бронированиями.

### Параметры

| Параметр | Тип | Смысл |
|---|---|---|
| `clientId` | `Long` | id существующего клиента |
| `roomId` | `Long` | id существующего номера |
| `checkIn` | `LocalDate` | дата заезда |
| `checkOut` | `LocalDate` | дата выезда (строго позже заезда) |
| `guestCount` | `int` | количество гостей |

### Последовательность выполнения

1. **`clientService.getById(clientId)`** — достаёт клиента.
   Внутри: `clientRepository.findById(id)` возвращает `Optional<Client>`;
   если клиента нет, `orElseThrow` бросает `ClientNotFoundException`.
2. **`roomService.getById(roomId)`** — достаёт номер.
   Внутри: `roomRepository.findById(id)`; если номера нет — `RoomNotFoundException`.
3. **`new Booking(room, client, checkIn, checkOut, guestCount)`** — создаёт
   доменный объект. Конструктор:
   - проверяет, что номер и клиент не `null`;
   - `validateDates`: даты не `null`, `checkOut` строго позже `checkIn`,
     `checkIn` не раньше сегодняшнего дня;
   - `validateGuestCount`: гостей больше нуля и
     `room.canAccommodate(guestCount)`;
   - **фиксирует цену** `pricePerNight = room.getPricePerNight()`;
   - ставит статус `CREATED`.
4. **Проверка пересечения дат**:
   - `bookingRepository.findByRoomIdAndStatusIn(roomId, BookingStatus.activeStatuses())` —
     Spring Data JPA выполняет запрос
     `... where room_id = ? and status in ('CREATED', 'CONFIRMED')`;
   - `activeStatuses()` возвращает `EnumSet` активных статусов;
   - `.anyMatch(existing -> existing.overlaps(checkIn, checkOut))` — есть ли
     хотя бы одна бронь с пересечением.
   - `overlaps` реализован так:
     `this.checkIn.isBefore(otherCheckOut) && otherCheckIn.isBefore(this.checkOut)`.
     Период — полуинтервал `[заезд, выезд)`, поэтому заезд в день чужого
     выезда конфликтом не считается.
5. Если пересечение есть — **`throw new RoomNotAvailableException(...)`**.
   До `save` дело не доходит, «битая» запись в БД не появляется.
6. **`bookingRepository.save(booking)`** — JPA выполняет `INSERT` и присваивает
   `id` из PostgreSQL (`BIGSERIAL`). Возвращается управляемая сущность.
7. **`client.addBooking(saved)`** — добавляет бронь в коллекцию клиента
   (обратная сторона связи `Client → Booking`).
8. **`return saved`** — возвращает сохранённый объект с `id` и статусом `CREATED`.

### Что возвращается

Объект `Booking` с:
- `id` (выдан базой);
- зафиксированной `pricePerNight`;
- статусом `CREATED`;
- датами, клиентом и номером.

Ночи и итоговая стоимость **не хранятся** — они вычисляются по запросу:
`getNights()` через `ChronoUnit.DAYS.between`, `calculateTotal()` —
`pricePerNight * nights`.

### Почему порядок именно такой

Сначала находим и проверяем всё, что нужно, и только в конце сохраняем.
Если на любом шаге выброшено исключение, транзакция откатывается —
в БД ничего не попало. Это прямое выполнение требования «ошибочные операции
не должны приводить к некорректному состоянию объектов».

`@Transactional` — граница транзакции: либо все изменения фиксируются,
либо ни одно.

### Возможные вопросы преподавателя

- **Почему цена фиксируется в бронировании?** Это исторический документ:
  если отель завтра поднимет цену, уже оформленная бронь должна остаться
  по старой цене. В БД поле `price_per_night` хранится отдельно от `rooms`.
- **Почему проверка пересечения в сервисе, а не в `Booking`?** Одному
  бронированию неизвестны другие бронирования. Правило требует посмотреть
  на *другие* объекты — значит, это ответственность сервиса.
- **Почему `LocalDate`, а не `Date`?** Для гостиницы важны календарные даты,
  а не моменты времени с часовым поясом.
- **Что будет при повторном вызове?** Если даты пересекаются с активной
  бронью — `RoomNotAvailableException` (409); если нет — будет создана вторая бронь.
- **Почему `save` возвращает объект?** После `persist` JPA присваивает `id`;
  возвращённая сущность уже управляемая и содержит сгенерированный ключ.

## 2. Четыре принципа ООП

### 1. Абстракция

**Определение:** выделяем существенные для задачи свойства и поведение,
скрываем несущественные детали реализации.

**В проекте:**
- `AbstractEntity` — абстрактный класс, описывающий общее для всех сущностей:
  `id`, `equals`, `hashCode`. Конкретные сущности не думают о том, как хранится id.
- `DomainException` — абстрактное базовое исключение; конкретные ошибки
  описывают только свой смысл.
- Репозитории — интерфейсы `JpaRepository`. Сервис не знает, как именно
  Spring Data реализует `findById`, — он работает с абстракцией.
- `Room implements Comparable<Room>` — для сортировки важно только то, что
  номера сравнимы по цене; детали скрыты в `compareTo`.
- Сервисы предоставляют предметные операции (`create`, `confirm`,
  `findAvailable`), а не «достань EntityManager и покопайся».

### 2. Инкапсуляция

**Определение:** поля закрыты, доступ к состоянию — только через методы,
которые проверяют правила.

**В проекте:**
- Все поля сущностей `private`.
- Состояние меняется через методы с валидацией: `Hotel.setName`,
  `Room.update`, `Client.setEmail`.
- `Hotel.getRooms()` возвращает `Collections.unmodifiableList(rooms)` —
  снаружи нельзя добавить номер в обход `Hotel.addRoom`.
- У `Booking` нет `setStatus`: статус меняется только через
  `confirm()`, `cancel()`, `complete()`, и каждый метод проверяет текущее
  состояние. Нельзя «снаружи» поставить `COMPLETED` отменённой брони.
- `Client.getBookings()` также отдаёт неизменяемый список.
- JPA-ограничения (`nullable = false`, `unique = true`) дублируют важные
  инварианты на уровне БД.

Пример:

```java
private BookingStatus status;

public void confirm() {
    if (status != BookingStatus.CREATED) {
        throw new InvalidBookingStateException(
                "Подтвердить можно только бронирование в статусе CREATED...");
    }
    status = BookingStatus.CONFIRMED;
}
```

### 3. Наследование

**Определение:** один класс наследует поля и методы другого, повторно
используя общее поведение.

**В проекте:**
- `Hotel`, `Room`, `Client`, `Booking`, `RoomType` наследуют
  `AbstractEntity` — получают `id`, `equals`, `hashCode`.
- Иерархия исключений:
  `DomainException → EntityNotFoundException → HotelNotFoundException`
  и `DomainException → BusinessRuleException → RoomNotAvailableException`.
- Репозитории наследуют `JpaRepository<T, ID>` — получают `save`, `findById`,
  `findAll`, `delete` и другие методы.

Наследование применено только там, где есть реальная общая часть.
Искусственной иерархии вроде `Hotel extends Building` в проекте нет.

### 4. Полиморфизм

**Определение:** один и тот же вызов ведёт себя по-разному в зависимости
от фактического типа объекта.

**В проекте:**
- `GlobalExceptionHandler` объявляет обработчики для `EntityNotFoundException`
  и `BusinessRuleException`; конкретные `HotelNotFoundException`,
  `RoomNotAvailableException` обрабатываются через общий тип.
- `Room.compareTo` вызывается внутри `sorted()`; Stream не знает, что
  сортирует именно номера, — он использует контракт `Comparable`.
- Сервис зависит от интерфейса `BookingRepository`, а Spring подставляет
  сгенерированную реализацию — классический полиморфизм через интерфейс.
- `Optional.orElseThrow(() -> new HotelNotFoundException(id))` —
  в разных сервисах передаются разные фабрики исключений, а код обработки
  отсутствия один и тот же.

### Бонус: композиция

В проекте активно используется композиция:
- `Hotel` содержит `List<Room>`;
- `Client` содержит `List<Booking>`;
- `Booking` содержит ссылки на `Room` и `Client`;
- контроллеры содержат сервисы, сервисы — репозитории.

Композиция выбрана там, где объект «владеет» другим объектом или состоит
из него. Это гибче наследования и лучше отражает предметную область.

## 3. `==` и `equals()`

### `==`

- Для **примитивов** (`int`, `long`, `boolean`, ...) сравнивает **значения**.
- Для **ссылочных типов** сравнивает **адреса объектов**, то есть являются ли
  две переменные ссылками на один и тот же объект в памяти.

```java
int a = 5;
int b = 5;
a == b                       // true — значения равны

String s1 = "101";
String s2 = new String("101");
s1 == s2                     // false — разные объекты
s1.equals(s2)                // true  — одинаковое содержимое
```

### `equals()`

- Метод из `Object`; по умолчанию делает то же, что `==` (сравнение ссылок).
- Переопределяется, чтобы сравнивать **содержимое** или **идентичность**
  объекта.
- При переопределении `equals` **обязательно** переопределять `hashCode`:
  равные объекты должны давать одинаковый хеш, иначе `HashSet`/`HashMap`
  будут работать неправильно.

### Примеры из проекта

**Строки — сравниваем содержимое:**

```java
// ClientService: email уже нормализован в нижний регистр
client.getEmail().equalsIgnoreCase(email)

// HotelService.search: город без учёта регистра
hotel.getCity().equalsIgnoreCase(city.trim())

// Hotel.addRoom: номера комнат "101" и "101" — это один и тот же номер
existing.getNumber().equalsIgnoreCase(room.getNumber())
```

Если написать `existing.getNumber() == room.getNumber()`, сравнятся ссылки,
и одинаковые по смыслу строки могут оказаться «разными».

**Сущности — сравниваем по `id`:**

```java
@MappedSuperclass
public abstract class AbstractEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (!(other instanceof AbstractEntity that)) return false;
        if (Hibernate.getClass(this) != Hibernate.getClass(that)) return false;
        return id != null && id.equals(that.id);
    }

    @Override
    public int hashCode() {
        return Hibernate.getClass(this).hashCode();
    }
}
```

Две сущности одного типа с одинаковым `id` — это одна и та же строка БД.
Сущности без `id` (ещё не сохранённые) равны только сами себе.

`Hibernate.getClass(...)` нужен, потому что Hibernate может вернуть
прокси-подкласс; обычный `getClass()` у прокси и у сущности различается.

`hashCode` не зависит от `id`, потому что id появляется только после `INSERT`.
Если бы хеш менялся после сохранения, объект «терялся» бы в `HashSet`.

**Enum — можно и нужно `==`:**

```java
if (status == BookingStatus.CANCELLED) { ... }
```

У enum-констант в JVM ровно один экземпляр на значение, поэтому `==`
безопасен и даже предпочтителен.

**`BigDecimal` — только `compareTo`, не `equals`:**

```java
booking.calculateTotal().compareTo(new BigDecimal("20000")) == 0
```

`BigDecimal.equals` учитывает масштаб (scale): `new BigDecimal("4000")`
и `new BigDecimal("4000.00")` **не равны** через `equals`, хотя обозначают
одну сумму. Поэтому в проекте везде используется `compareTo`.

### Короткий ответ

`==` сравнивает значения примитивов или ссылки на объекты, `equals` —
содержимое/логическую идентичность. В проекте строки и email сравниваются
через `equals`/`equalsIgnoreCase`, сущности — через переопределённый
`equals` по `id`, enum — через `==`, деньги — через `compareTo`.

## 4. `List`, `Set`, `Map`

### Сравнение

| Коллекция | Порядок | Дубликаты | Доступ | Типичное применение |
|---|---|---|---|---|
| `List` | есть, по индексу | разрешены | по индексу, `get(i)` | упорядоченные результаты, коллекции внутри сущностей |
| `Set` | обычно нет (у `HashSet`) | запрещены | только перебор/`contains` | уникальные значения, membership-проверки |
| `Map` | зависит от реализации | ключи уникальны | по ключу, `get(key)` | поиск по ключу, справочники, статистика |

### Выбор в проекте

#### `List` — упорядоченные коллекции и результаты

- `Hotel.rooms` — `List<Room>`: номера отеля перебираются и выводятся
  в порядке добавления; JPA-связь `@OneToMany` стандартно описывается списком.
- `Client.bookings` — `List<Booking>`: история бронирований.
- Результаты Stream-запросов (`findAvailable`, `getRooms`, `search`) —
  `List`, потому что это упорядоченная последовательность.
- `List` выбран, а не `Set`, потому что:
  - нужен порядок и доступ по индексу;
  - уникальность номера комнаты обеспечивается бизнес-правилом
    `Hotel.addRoom` и ограничением БД `UNIQUE (hotel_id, number)`,
    а не коллекцией;
  - `Set` сущностей с генерируемым `id` и прокси Hibernate — более
    сложный и менее предсказуемый вариант.

#### `Set` — уникальные статусы

`BookingStatus.activeStatuses()`:

```java
public static Set<BookingStatus> activeStatuses() {
    return EnumSet.of(CREATED, CONFIRMED);
}
```

Почему `Set`:

- статусы уникальны по смыслу — дубликаты невозможны;
- `EnumSet` очень компактен и быстро проверяет вхождение;
- порядок не важен, потому что это условие для SQL `IN (...)`.

Исторически на этапе 2 `Set` также использовался для уникальных email
и названий типов номеров. В финальной версии эту роль выполняет
ограничение `UNIQUE` в PostgreSQL + проверки `existsByEmailIgnoreCase`
и `existsByNameIgnoreCase`.

#### `Map` — статистика по статусам

`BookingStatistics`:

```java
Map<BookingStatus, Long> countByStatus = filtered.stream()
        .collect(Collectors.groupingBy(
                Booking::getStatus,
                () -> new EnumMap<>(BookingStatus.class),
                Collectors.counting()));
```

Почему `Map`:

- нужно хранить пару «статус → количество»;
- ключи уникальны;
- `EnumMap` хранит ключи-enum компактно и в порядке объявления констант,
  поэтому вывод статистики предсказуем.

#### `Optional` — не коллекция

`Optional<T>` используется как безопасный результат поиска, который может
отсутствовать: `findById`, `findByEmail`, `findCheapestAvailable`,
`getAveragePrice`. Это не хранилище множества объектов.

### Короткий ответ

`List` — упорядоченная последовательность с дубликатами, `Set` — уникальные
элементы, `Map` — пары «ключ → значение» с уникальными ключами. В проекте
`List` используется для коллекций сущностей и результатов запросов,
`EnumSet` — для активных статусов, `EnumMap` — для статистики по статусам.

## 5. JPA-сущность и аннотации `@Entity`, `@Table`, `@Id`

### Что такое JPA-сущность

**JPA-сущность** — это Java-класс, экземпляры которого JPA (Hibernate)
отображает на строки таблицы базы данных. Сущность:

- управляется `EntityManager` (в Spring — через репозитории);
- имеет первичный ключ;
- имеет конструктор без аргументов (хотя бы `protected`) — Hibernate
  создаёт объекты отражением;
- не должна быть `final` (Hibernate может создавать прокси-подклассы);
- может иметь связи с другими сущностями.

В проекте сущности: `Hotel`, `Room`, `RoomType`, `Client`, `Booking`.

### `@Entity`

Помечает класс как сущность. JPA понимает, что объекты этого класса нужно
хранить в БД.

```java
@Entity
public class Booking { ... }
```

По умолчанию именем таблицы станет имя класса (`Booking`), но обычно
имя задают явно через `@Table`.

### `@Table`

Настраивает таблицу: имя, схему, ограничения, индексы.

```java
@Entity
@Table(
    name = "bookings",
    indexes = {
        @Index(name = "idx_booking_room_dates",
               columnList = "room_id, check_in, check_out"),
        @Index(name = "idx_booking_client", columnList = "client_id")
    }
)
public class Booking { ... }
```

Зачем:
- имя таблицы в БД может отличаться от имени класса (`bookings`);
- можно задать уникальные ограничения (`uniqueConstraints`);
- можно добавить индексы под частые запросы (поиск броней номера по датам).

### `@Id`

Обязательная аннотация: помечает поле первичного ключа.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
@Column(name = "id")
private Long id;
```

- `@GeneratedValue(strategy = IDENTITY)` — id выдаёт сама БД
  (в PostgreSQL — `BIGSERIAL`).
- `SEQUENCE` — id из последовательности.
- `AUTO` — стратегию выбирает провайдер.

В проекте `@Id` и `@GeneratedValue` вынесены в `AbstractEntity`
с `@MappedSuperclass`, поэтому все сущности получают одинаковый id.

### Пример `Booking` в проекте

```java
@Entity
@Table(name = "bookings", indexes = { ... })
public class Booking extends AbstractEntity {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "room_id", nullable = false)
    private Room room;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "client_id", nullable = false)
    private Client client;

    @Column(name = "check_in", nullable = false)
    private LocalDate checkIn;

    @Column(name = "check_out", nullable = false)
    private LocalDate checkOut;

    @Column(name = "guest_count", nullable = false)
    private int guestCount;

    @Column(name = "price_per_night", nullable = false,
            precision = 10, scale = 2)
    private BigDecimal pricePerNight;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private BookingStatus status;

    /** Требуется JPA/Hibernate. */
    protected Booking() {
    }

    // конструктор с правилами и методы — как в проекте
}
```

### Таблица `bookings`

```sql
CREATE TABLE bookings (
    id              BIGSERIAL PRIMARY KEY,
    check_in        DATE          NOT NULL,
    check_out       DATE          NOT NULL,
    guest_count     INT           NOT NULL,
    price_per_night NUMERIC(10,2) NOT NULL,
    status          VARCHAR(20)   NOT NULL,
    client_id       BIGINT        NOT NULL REFERENCES clients (id),
    room_id         BIGINT        NOT NULL REFERENCES rooms (id)
);
```

### Важные детали для JPA

- нужен конструктор без аргументов (`protected Booking() {}`);
- поля не `final`, иначе Hibernate не сможет их заполнить;
- `@Enumerated(EnumType.STRING)` хранит статус строкой, а не числом;
- `equals`/`hashCode` учитывают прокси Hibernate (см. вопрос 3);
- `@Column(precision = 10, scale = 2)` задаёт точность денег в БД.

## 6. Виды связей в JPA

### Основные виды

| Связь | Аннотация | Смысл | Пример |
|---|---|---|---|
| один к одному | `@OneToOne` | одной строке соответствует ровно одна | Клиент ↔ Паспорт (в проекте нет) |
| один ко многим | `@OneToMany` | одной строке соответствует много | Отель → Номера |
| многие к одному | `@ManyToOne` | много строк ссылаются на одну | Номер → Отель |
| многие ко многим | `@ManyToMany` | много ↔ много через промежуточную таблицу | Номер ↔ Удобства (если добавить `Amenity`) |

`@OneToMany` и `@ManyToOne` — две стороны одной связи.
Одна сторона **владеющая** (owning side), вторая — **обратная** (`mappedBy`).
Внешний ключ физически хранится на владеющей стороне.

### Вспомогательные аннотации

- `@JoinColumn(name = "hotel_id")` — имя столбца внешнего ключа.
- `@JoinTable(...)` — промежуточная таблица для `@ManyToMany`.
- `mappedBy = "hotel"` — «я не владею связью, смотри поле `hotel`
  в классе `Room`».
- `cascade = CascadeType.ALL` — операции с родителем каскадно применяются
  к детям.
- `orphanRemoval = true` — удаление ребёнка при удалении из коллекции.
- `fetch = FetchType.LAZY` — загружать связь только при обращении.

### Связи в проекте

```
Hotel 1 ────── * Room        (у отеля много номеров)
Room  * ────── 1 RoomType    (у номера один тип)
Client 1 ───── * Booking     (у клиента много броней)
Room 1 ─────── * Booking     (номер участвует во многих бронях)
Booking * ──── 1 Room        (бронь относится к одному номеру)
Booking * ──── 1 Client      (бронь оформлена одним клиентом)
```

Разметка:

```java
// Hotel — обратная сторона связи
@OneToMany(mappedBy = "hotel", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Room> rooms = new ArrayList<>();

// Room — владеющая сторона, здесь будет hotel_id
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "hotel_id", nullable = false)
private Hotel hotel;

// Room — тип номера
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "room_type_id", nullable = false)
private RoomType roomType;

// Client — обратная сторона
@OneToMany(mappedBy = "client")
private List<Booking> bookings = new ArrayList<>();

// Booking — владеющая сторона
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "room_id", nullable = false)
private Room room;

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "client_id", nullable = false)
private Client client;
```

### Почему именно так

- **`Hotel → Room` — композиция.** Номера не существуют без отеля, поэтому
  `cascade = ALL` и `orphanRemoval = true` уместны.
- **`Room → Hotel` — `@ManyToOne`.** Именно здесь хранится `hotel_id`;
  `mappedBy` в `Hotel` говорит, что владелец — поле `hotel` в `Room`.
- **`Booking → Room` и `Booking → Client` — `@ManyToOne`.** У брони ровно
  один номер и один клиент; обратные коллекции нужны для навигации.
- **`Client → Booking` — `@OneToMany` без каскадного удаления.** Бронирования
  — это история; удалять их вместе с клиентом нельзя.
- **`@ManyToMany` в обязательной модели нет.** Оно появилось бы, если
  добавить `Amenity` (удобства номера) — тогда понадобилась бы таблица
  `room_amenities`. Искусственно вводить `@ManyToMany` не нужно.
- **`fetch = LAZY`** для `@ManyToOne` уменьшает объём загружаемых данных;
  DTO собираются в рамках HTTP-запроса (OSIV), поэтому прокси догружаются
  безопасно.

### Важно про JSON и двусторонние связи

Если вернуть сущность с двусторонними связями напрямую в REST, Jackson
может уйти в бесконечную рекурсию (`Booking → Room → Hotel → rooms → ...`).
В проекте эта проблема решена **DTO**:

- `BookingResponse` — плоская структура с `bookingId`, `roomId`, `hotelId`,
  `clientId`, `nights`, `total`, `status`;
- `RoomResponse` — `hotelId`, `hotelName`, `roomTypeId`, `roomTypeName`;
- `HotelResponse` — без вложенного списка номеров, только `roomCount`.

## 7. Исключения, `throw` и `catch`

### Зачем нужны исключения

- **Сигнализируют об ошибке** и прерывают нормальный сценарий.
- **Не позволяют продолжить работу в некорректном состоянии**: если даты
  неверны, бронь не создаётся.
- **Разделяют нормальный и ошибочный потоки**: не нужно возвращать `null`
  или коды ошибок и проверять их после каждого вызова.
- **Позволяют централизованно обработать ошибки**: `@RestControllerAdvice`
  превращает исключение в JSON и HTTP-код.
- **Сохраняют диагностику**: сообщение, тип, стек вызовов.

### Иерархия в проекте

```
RuntimeException
└── DomainException                  errorCode
    ├── EntityNotFoundException      "ENTITY_NOT_FOUND"
    │   ├── HotelNotFoundException
    │   ├── RoomNotFoundException
    │   ├── RoomTypeNotFoundException
    │   ├── ClientNotFoundException
    │   └── BookingNotFoundException
    └── BusinessRuleException        "BUSINESS_RULE_VIOLATION"
        ├── RoomNotAvailableException
        ├── InvalidBookingDatesException
        ├── RoomCapacityExceededException
        ├── InvalidBookingStateException
        └── DuplicateEntityException
```

### Собственное исключение: `RoomNotAvailableException`

```java
public class RoomNotAvailableException extends BusinessRuleException {

    public RoomNotAvailableException(Long roomId, Object checkIn, Object checkOut) {
        super("Номер " + roomId + " недоступен на период " + checkIn + " — " + checkOut
                + ": уже есть активное бронирование на пересекающиеся даты");
    }
}
```

**Где возникает:** `BookingService.create`, когда `anyMatch` нашёл активную
бронь с пересечением дат.

**Где обрабатывается:** в `GlobalExceptionHandler`:

```java
@ExceptionHandler({
        RoomNotAvailableException.class,
        InvalidBookingStateException.class,
        DuplicateEntityException.class
})
public ResponseEntity<ErrorResponse> handleConflict(BusinessRuleException e) {
    return ResponseEntity
            .status(HttpStatus.CONFLICT)
            .body(new ErrorResponse(e.getErrorCode(), e.getMessage()));
}
```

В бизнес-коде исключение не «глотается» — оно пробрасывается наверх,
а обработчик возвращает `409 Conflict` и JSON:

```json
{
  "error": "BUSINESS_RULE_VIOLATION",
  "message": "Номер 2 недоступен на период ..."
}
```

### `throw`

`throw` создаёт объект исключения и **прерывает** текущий метод. Управление
переходит к ближайшему подходящему `catch` вверх по стеку.

```java
if (conflict) {
    throw new RoomNotAvailableException(roomId, checkIn, checkOut);
}
```

`throws` в сигнатуре — другое: это объявление, что метод может выбросить
проверяемое исключение. В проекте `throws` не используется, потому что все
исключения — `RuntimeException` (непроверяемые).

### `catch`

`catch` перехватывает исключение и обрабатывает его. В Spring MVC роль
централизованного `catch` играет `@ExceptionHandler`:

```java
try {
    action.run();
} catch (DomainException e) {
    // обработать
}
```

Правила:
- ловить **наиболее конкретный** тип первым, общий — последним;
- не «глотать» исключение молча;
- если не можешь обработать — пробрось дальше или оберни в своё;
- `finally` выполняется всегда (закрытие ресурсов); для `AutoCloseable`
  лучше `try-with-resources`.

### Почему `RuntimeException`, а не проверяемое

Ошибки предметной области — это **нормальный результат неверного запроса**
(неверные даты, занятый номер), а не редкий сбой ввода-вывода. Если сделать
их проверяемыми, придётся добавлять `throws` во все методы цепочки
(`Controller → Service → Repository`), хотя обрабатывать их всё равно будет
один центральный обработчик. Кроме того, Spring по умолчанию откатывает
транзакцию именно при `RuntimeException`.

### Ошибочные сценарии для демонстрации

1. **Пересечение дат.** Номер уже забронирован на 15–20 ноября; пробуем
   создать бронь на 16–18 ноября → `RoomNotAvailableException`, HTTP 409.
2. **Превышение вместимости.** Номер вмещает 2 гостей, передаём 3 →
   `RoomCapacityExceededException`, HTTP 400.
3. **Подтверждение отменённой брони** → `InvalidBookingStateException`, 409.
4. **Несуществующий отель** → `HotelNotFoundException`, 404.
5. **Повторный email** → `DuplicateEntityException`, 409.

### Главное правило

Проверки выполняются **до** сохранения, а транзакция откатывается при
исключении. Если операция не удалась, в БД не появляется частично
заполненная или противоречивая запись.

## 8. Примеры Stream API

Stream API в проекте используется в сервисах и при маппинге DTO.

### 1. Фильтрация + сортировка: номера по вместимости и цене

`HotelService.getRooms`:

```java
return roomRepository.findByHotelId(hotelId).stream()
        .filter(room -> minCapacity == null || room.getCapacity() >= minCapacity)
        .filter(room -> minPrice == null
                || room.getPricePerNight().compareTo(minPrice) >= 0)
        .filter(room -> maxPrice == null
                || room.getPricePerNight().compareTo(maxPrice) <= 0)
        .sorted()
        .toList();
```

Результат: список подходящих номеров, отсортированный по цене
(`Room implements Comparable<Room>`).

### 2. Поиск + сортировка: отели по городу и части названия

`HotelService.search`:

```java
List<Hotel> hotels = hotelRepository.findByCityIgnoreCase(city.trim()).stream()
        .filter(hotel -> hotel.getName().toLowerCase().contains(normalizedNamePart))
        .toList();

return hotels.stream()
        .sorted(Comparator.comparing(Hotel::getName))
        .toList();
```

Результат: найденные отели в алфавитном порядке.
Производный запрос Spring Data достаёт отели города, Stream фильтрует
по названию и сортирует.

### 3. `anyMatch`: есть ли пересечение дат

`BookingService.create`:

```java
boolean conflict = bookingRepository
        .findByRoomIdAndStatusIn(roomId, BookingStatus.activeStatuses())
        .stream()
        .anyMatch(existing -> existing.overlaps(checkIn, checkOut));
```

Результат: `true`, если хотя бы одна активная бронь пересекается с периодом.
`anyMatch` — короткозамкнутая операция: остановится на первом совпадении.

### 4. `min` + `Optional`: самый дешёвый свободный номер

`RoomService.findCheapestAvailable`:

```java
return findAvailable(hotelId, checkIn, checkOut, guestCount).stream()
        .min(Comparator.naturalOrder());
```

Результат: `Optional<Room>` — либо самый дешёвый номер, либо пустой
`Optional`, если свободных нет.

### 5. `map` + `reduce`: сумма стоимости бронирований

`BookingService.getStatistics`:

```java
BigDecimal totalRevenue = payable.stream()
        .map(Booking::calculateTotal)
        .reduce(BigDecimal.ZERO, BigDecimal::add);
```

Результат: суммарная стоимость неотменённых броней. `map` преобразует
`Booking` в `BigDecimal`, `reduce` сворачивает всё в одно значение.

### 6. `groupingBy` + `counting`: группировка по статусу

```java
Map<BookingStatus, Long> countByStatus = filtered.stream()
        .collect(Collectors.groupingBy(
                Booking::getStatus,
                () -> new EnumMap<>(BookingStatus.class),
                Collectors.counting()));
```

Результат: `{CREATED=1, CONFIRMED=2, CANCELLED=1}` —
количество броней по каждому статусу. `EnumMap` сохраняет порядок статусов.

### 7. `map` + `reduce` + деление: средняя цена

`RoomService.getAveragePrice`:

```java
BigDecimal sum = rooms.stream()
        .map(Room::getPricePerNight)
        .reduce(BigDecimal.ZERO, BigDecimal::add);
return Optional.of(sum.divide(
        BigDecimal.valueOf(rooms.size()), 2, RoundingMode.HALF_UP));
```

Результат: средняя цена за ночь, округлённая до копеек, в `Optional`
(пустой, если номеров нет).

### 8. `noneMatch`: свободен ли номер

`RoomService.isFree`:

```java
return bookingRepository
        .findByRoomIdAndStatusIn(room.getId(), BookingStatus.activeStatuses())
        .stream()
        .noneMatch(existing -> existing.overlaps(checkIn, checkOut));
```

Результат: `true`, если ни одна активная бронь не пересекается с периодом.

### 9. `map` при сборке DTO

```java
return hotelService.search(city, name).stream()
        .map(HotelResponse::from)
        .toList();
```

Результат: список JSON-объектов вместо списка сущностей.

### Что важно сказать

- Stream **не изменяет исходную коллекцию** — создаёт новую последовательность.
- Промежуточные операции (`filter`, `map`, `sorted`) ленивы; выполнение
  начинается только на терминальной (`toList`, `reduce`, `collect`,
  `anyMatch`, `min`).
- `toList()` (Java 16+) возвращает неизменяемый список.
- Для денег используется `BigDecimal`, поэтому сумма — `reduce` с
  `BigDecimal::add`, а не `sum()`.

## 9. Промежуточные и терминальные операции Stream

### Промежуточные (intermediate)

Возвращают **новый Stream**, не запускают вычисления, могут объединяться
в цепочку.

Примеры: `filter`, `map`, `flatMap`, `sorted`, `distinct`, `limit`,
`skip`, `peek`, `mapToInt`, `boxed`.

```java
stream
    .filter(room -> room.canAccommodate(guestCount)) // промежуточная
    .map(Room::getPricePerNight)                     // промежуточная
    .sorted()                                        // промежуточная
```

### Терминальные (terminal)

Запускают выполнение цепочки и возвращают **результат** (значение,
коллекцию, `Optional`) или `void`. После терминальной операции Stream
считается использованным.

Примеры: `toList`, `collect`, `forEach`, `count`, `reduce`, `min`, `max`,
`anyMatch`, `allMatch`, `noneMatch`, `findFirst`, `findAny`.

```java
List<Room> result = stream
    .filter(...)
    .sorted()
    .toList();          // терминальная — здесь всё выполняется
```

### Пример из проекта: `RoomService.findAvailable`

```java
return roomRepository.findByHotelId(hotelId).stream()          // источник
        .filter(room -> room.canAccommodate(guestCount))       // промежуточная
        .filter(room -> isFree(room, checkIn, checkOut))       // промежуточная
        .sorted()                                              // промежуточная
        .toList();                                             // терминальная
```

- `filter` и `sorted` только описывают преобразования;
- реальная работа начинается при `toList()`;
- результат — новый `List<Room>`.

### Пример: `anyMatch`

```java
boolean conflict = bookings.stream()
        .filter(Booking::isActive)                 // промежуточная
        .anyMatch(b -> b.overlaps(checkIn, checkOut)); // терминальная
```

`anyMatch` — **короткозамкнутая** терминальная операция: как только найден
первый подходящий элемент, дальнейшая обработка прекращается. Аналогично
`findFirst` и `findAny`.

### Важные свойства

- Stream **одноразовый**: после терминальной операции повторно использовать
  его нельзя, нужно создавать новый.
- Промежуточные операции **ленивы**: без терминальной ничего не выполнится.
- `peek` — для отладки, не для бизнес-логики.
- Параллельные Stream в этом проекте не нужны: данных немного, а
  изменяемое состояние и JPA-сессия не предназначены для параллельной
  обработки.

## 10. Controller, Service, Repository и MVC

### Слои и их ответственность

| Слой | Что делает | Чего не делает |
|---|---|---|
| **Controller** | принимает HTTP-запрос, извлекает параметры, вызывает сервис, формирует HTTP-ответ и код, валидирует DTO | не содержит бизнес-правил, не работает с БД напрямую |
| **Service** | выполняет сценарий, оркестрирует доменные объекты и репозитории, проверяет межобъектные правила, управляет транзакциями | не знает про HTTP и JSON |
| **Repository** | сохраняет и достаёт данные, выполняет запросы | не содержит бизнес-логики |
| **Model / Domain** | сущности, их состояние и поведение, инварианты | не знает про HTTP и Spring |

Направление зависимостей:

```
HTTP request
    ↓
Controller  →  Service  →  Repository  →  Database
                   ↓
              Domain model
```

### Как это сделано в проекте

- `HotelController`, `RoomController`, `BookingController`,
  `ClientController`, `RoomTypeController` — `@RestController`.
- `HotelService`, `RoomService`, `BookingService`, `ClientService`,
  `RoomTypeService` — `@Service` + `@Transactional`.
- `HotelRepository`, `RoomRepository`, `BookingRepository`,
  `ClientRepository`, `RoomTypeRepository` — интерфейсы `JpaRepository`.
- `Hotel`, `Room`, `RoomType`, `Client`, `Booking` — JPA-сущности.
- `dto/request` и `dto/response` — вход/выход API.
- `GlobalExceptionHandler` — `@RestControllerAdvice`.

Пример контроллера:

```java
@RestController
@RequestMapping("/api/bookings")
public class BookingController {

    private final BookingService bookingService;

    public BookingController(BookingService bookingService) {
        this.bookingService = bookingService;
    }

    @PostMapping
    public ResponseEntity<BookingResponse> create(@Valid @RequestBody BookingRequest request) {
        Booking booking = bookingService.create(
                request.clientId(),
                request.roomId(),
                request.checkIn(),
                request.checkOut(),
                request.guestCount());
        return ResponseEntity
                .created(URI.create("/api/bookings/" + booking.getId()))
                .body(BookingResponse.from(booking));
    }
}
```

- `@RestController` = `@Controller` + `@ResponseBody`;
- `@RequestMapping` — общий префикс;
- `@Valid` — валидация DTO;
- `ResponseEntity.created(...)` — `201` + `Location`;
- `BookingResponse.from(...)` — маппинг сущности в DTO.

### Зачем разделять ответственность

- **Одна причина для изменения.** Поменялся URL или формат JSON — правим
  только контроллер. Поменялась БД — только репозиторий. Поменялось
  бизнес-правило — сервис или домен.
- **Проверяемость.** Домен и сервисы можно проверять отдельно, а REST —
  реальными HTTP-запросами через Postman.
- **Повторное использование.** Один сервис можно вызвать из REST,
  планировщика, консоли.
- **Защита от «бизнес-логики в контроллере».**
- **Транзакции.** Граница транзакции проходит по методу сервиса.

### MVC

**MVC (Model–View–Controller)** — архитектурный паттерн разделения
приложения на три части:

- **Model** — данные и правила предметной области (`Hotel`, `Room`,
  `Booking`, сервисы);
- **View** — представление результата (в REST это JSON);
- **Controller** — принимает запрос, вызывает модель и выбирает представление.

В REST-приложении:

```
Клиент → Controller → Service → Model/Repository
                ↓
          JSON (View)
```

Controller не должен сам считать стоимость, проверять пересечение дат или
ходить в БД. Он принимает запрос, делегирует сервису и возвращает результат.

### Полный сценарий `POST /api/bookings`

1. `BookingController` получает JSON, Jackson превращает его в `BookingRequest`.
2. `@Valid` проверяет поля; ошибка → `400`.
3. Контроллер вызывает `bookingService.create(...)`.
4. Сервис через репозитории находит клиента и номер; нет → `404`.
5. Создаёт `Booking` — домен проверяет даты и вместимость; ошибка → `400`.
6. Проверяет пересечение с активными бронями номера; есть → `409`.
7. Сохраняет бронь через `BookingRepository` (`INSERT`).
8. Контроллер возвращает `201 Created` + DTO:
   `{bookingId, nights, pricePerNight, total, status}`.
9. Если было исключение — `GlobalExceptionHandler` возвращает JSON ошибки
   и нужный HTTP-код.

## 11. HTTP-методы и HTTP-коды

### HTTP-методы

| Метод | Назначение | Идемпотентный | Пример |
|---|---|---|---|
| **GET** | получить данные, ничего не меняет | да | `GET /api/hotels/1` |
| **POST** | создать объект или выполнить действие | обычно нет | `POST /api/bookings`, `POST /api/bookings/1/confirm` |
| **PUT** | полностью заменить объект | да | `PUT /api/hotels/1` |
| **PATCH** | частично изменить объект | да (при корректной реализации) | `PATCH /api/hotels/1` |
| **DELETE** | удалить объект | да | `DELETE /api/hotels/1` |

- **GET** не должен менять состояние. Повторный запрос безопасен.
- **POST** создаёт новую сущность (или запускает действие). Повторный
  `POST /api/bookings` создаст вторую бронь, если даты не пересекаются.
- **PUT** присылает полное новое состояние; повтор с теми же данными даёт
  тот же результат. В проекте так обновляются отель, номер и клиент.
- **PATCH** присылает только изменяемые поля. В текущей версии не используется,
  потому что обновление полное; при необходимости добавляется отдельный DTO.
- **DELETE** повторный вызов обычно даёт `404`, но состояние системы
  от этого не меняется — метод идемпотентен.

### Выбор HTTP-кодов

| Код | Когда |
|---|---|
| `200 OK` | данные получены или изменены |
| `201 Created` | объект создан (`POST`), с заголовком `Location` |
| `204 No Content` | объект удалён, тело не нужно |
| `400 Bad Request` | некорректные входные данные: неверный JSON, даты, отрицательное число гостей, пустое имя |
| `404 Not Found` | объект не найден: отель, номер, клиент, бронь |
| `405 Method Not Allowed` | неподдерживаемый HTTP-метод |
| `409 Conflict` | операция нарушает бизнес-правило или состояние: номер занят, отменённую бронь нельзя подтвердить, отель с бронями нельзя удалить, дубликат email |
| `415 Unsupported Media Type` | неверный `Content-Type` |
| `500 Internal Server Error` | непредвиденная ошибка |

### Формат ошибки

```json
{
  "error": "ENTITY_NOT_FOUND",
  "message": "Отель с идентификатором 9999 не найден"
}
```

`error` берётся из `DomainException.getErrorCode()`; `message` — из
`getMessage()`.

### Централизованная обработка

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(EntityNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(EntityNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse(e.getErrorCode(), e.getMessage()));
    }

    @ExceptionHandler(BusinessRuleException.class)
    public ResponseEntity<ErrorResponse> handleBusinessRule(BusinessRuleException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ErrorResponse(e.getErrorCode(), e.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        String details = e.getBindingResult().getFieldErrors().stream()
                .map(error -> error.getField() + ": " + error.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ResponseEntity.badRequest()
                .body(new ErrorResponse("VALIDATION_ERROR", details));
    }
}
```

### Почему не все ошибки — `400`

`400` — «клиент прислал формально неверные данные».
`409` — «данные корректны, но операция конфликтует с текущим состоянием
системы»: номер уже занят, бронь уже отменена, отель нельзя удалить.
Это важное различие, его любят спрашивать.

### Почему `POST` для `confirm` и `cancel`

Это не создание объекта, а **предметное действие**, меняющее состояние.
`POST` подходит для действий, которые не сводятся к простой замене ресурса.
Повторный `confirm` уже подтверждённой брони должен вернуть `409`, а не
молча «сделать вид, что всё хорошо».

## Шпаргалка: ответ одной фразой

1. **`BookingService.create`** — находит клиента и номер, создаёт `Booking`
   (проверка дат и вместимости), проверяет пересечение с активными бронями,
   сохраняет и возвращает бронь.
2. **Четыре принципа** — абстракция (`AbstractEntity`, `JpaRepository`),
   инкапсуляция (`private` + методы), наследование (иерархия исключений),
   полиморфизм (`GlobalExceptionHandler`, `Comparable`, интерфейсы).
3. **`==` vs `equals`** — ссылки/значения примитивов vs содержимое;
   строки — `equals`, сущности — по `id`, enum — `==`, деньги — `compareTo`.
4. **`List`/`Set`/`Map`** — порядок и дубликаты / уникальность / ключ-значение;
   в проекте `List` для коллекций и результатов, `EnumSet` для статусов,
   `EnumMap` для статистики.
5. **JPA-сущность** — класс, отображённый на таблицу; `@Entity` — сущность,
   `@Table` — таблица, `@Id` — первичный ключ.
6. **Связи JPA** — `@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany`;
   в проекте `Hotel 1—* Room`, `Room *—1 RoomType`, `Client 1—* Booking`,
   `Booking *—1 Room`.
7. **Исключения** — сигнализируют об ошибке и защищают состояние;
   `throw` бросает, `catch` ловит; `RoomNotAvailableException` возникает
   в `BookingService.create`, обрабатывается `GlobalExceptionHandler` → 409.
8. **Stream API** — `filter`, `map`, `sorted`, `reduce`, `groupingBy`,
   `counting`, `min`, `anyMatch`; примеры — поиск номеров, статистика,
   самый дешёвый номер.
9. **Промежуточные vs терминальные** — `filter`/`map`/`sorted` ленивы и
   возвращают Stream; `toList`/`reduce`/`collect`/`anyMatch` запускают
   выполнение и возвращают результат.
10. **Controller/Service/Repository** — HTTP-адаптер / бизнес-логика /
    хранение; MVC делит Model, View (JSON), Controller.
11. **HTTP-методы** — GET читает, POST создаёт/действует, PUT заменяет,
    PATCH частично меняет, DELETE удаляет; коды — 200/201/204, 400, 404, 409.

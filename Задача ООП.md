## Общие требования

_Правила выполнения и защиты проекта по дисциплине «Объектно-ориентированное программирование»_

### 1. Результат семестровой работы

Итогом работы должно быть запускаемое Java-приложение на Spring Boot с REST API, бизнес-логикой и постоянным хранением данных в реляционной базе данных.

Проект выполняется последовательно: сначала создаётся объектная модель, затем хранение в коллекциях и бизнес-логика, после чего приложение переносится на Spring Boot и JPA.

### 2. Этапы проекта

|   |   |   |
|---|---|---|
|Этап|Что реализуется|Результат|
|Этап 1|Классы, объекты, связи, инкапсуляция, методы предметной области|Работающая доменная модель|
|Этап 2|Коллекции, бизнес-правила, исключения, Stream API, Optional|Приложение с данными в памяти|
|Этап 3|Spring Boot, REST, Controller–Service–Repository, JPA|API и база данных|
|Защита|Демонстрация и объяснение собственного решения|Итоговая оценка|

### 3. Обязательные требования к Java и ООП

- **Доменная модель:** выделены основные сущности, их свойства, поведение и связи.
    
- **Инкапсуляция:** поля закрыты от неконтролируемого изменения; состояние изменяется через методы.
    
- **Конструкторы и методы:** объекты можно корректно создать и использовать в бизнес-сценариях.
    
- **Композиция:** сложные объекты состоят из других объектов предметной области.
    
- **Интерфейс или наследование:** применяются только там, где это оправданно моделью; искусственная иерархия не требуется.
    
- **Объектное поведение:** проект не должен состоять только из геттеров, сеттеров и CRUD-операций.
    
- **equals, hashCode и toString:** реализуются для классов, где они необходимы для коллекций, сравнения и вывода.
    

### 4. Коллекции и обработка данных

До подключения базы данных проект должен хранить объекты в памяти. Тип коллекции выбирается осознанно.

- **List:** упорядоченная последовательность объектов;
    
- **Set:** хранение уникальных объектов;
    
- **Map:** быстрый поиск объекта по ключу;
    
- **Comparator или Comparable:** сортировка пользовательских объектов;
    
- **Optional:** безопасное представление результата поиска, который может отсутствовать.
    

В проекте должны быть показаны операции Stream API:

- фильтрация объектов;
    
- поиск;
    
- сортировка;
    
- преобразование данных;
    
- группировка;
    
- вычисление агрегированного значения: количества, суммы, среднего, минимума или максимума.
    

### 5. Исключения и ошибочные сценарии

Для ошибок предметной области необходимо создать собственные исключения. Ошибочные операции не должны приводить к некорректному состоянию объектов.

- запрошенный объект не существует;
    
- передано недопустимое значение;
    
- нарушено бизнес-правило;
    
- операция невозможна в текущем состоянии объекта.
    

```java
public class EntityNotFoundException extends RuntimeException { ... }
public class BusinessRuleException extends RuntimeException { ... }
```

### 6. Архитектура Spring Boot-приложения

```text
HTTP request
      ↓
Controller
      ↓
Service
      ↓
Repository
      ↓
Database
```

- **Controller:** принимает HTTP-запрос, извлекает параметры и формирует ответ.
    
- **Service:** выполняет бизнес-правила и изменяет состояние предметных объектов.
    
- **Repository:** получает и сохраняет данные.
    
- **Model:** содержит доменные и JPA-сущности.
    

> **Важно.** Основная бизнес-логика должна находиться в Service и доменных объектах, а не в Controller.

### 7. Требования к REST API

|   |   |
|---|---|
|Операция|Назначение|
|GET|Получение одного объекта, списка, результата поиска или аналитики|
|POST|Создание объекта или выполнение предметного действия|
|PUT / PATCH|Изменение существующего объекта или его состояния|
|DELETE|Удаление объекта, если это допускается предметной областью|

API должно принимать и возвращать JSON. Названия URL могут отличаться от примеров в теме, если сохраняется смысл операций.

|   |   |
|---|---|
|HTTP-код|Когда использовать|
|200 OK|Данные успешно получены или изменены|
|201 Created|Объект успешно создан|
|204 No Content|Объект успешно удалён|
|400 Bad Request|Некорректные входные данные|
|404 Not Found|Объект не найден|
|409 Conflict|Операция нарушает бизнес-правило или состояние объекта|

```json
{
  "error": "ENTITY_NOT_FOUND",
  "message": "Объект с идентификатором 15 не найден"
}
```

Отдельные DTO-классы допускаются, но не являются обязательным условием. Важно, чтобы структура JSON была понятной и не содержала циклических ссылок.

### 8. База данных и JPA

- подключена реляционная СУБД;
    
- основные классы представлены JPA-сущностями;
    
- для сущностей настроены идентификаторы;
    
- описаны необходимые связи между сущностями;
    
- используются Spring Data JPA repositories;
    
- данные сохраняются после перезапуска приложения;
    
- реализованы создание, чтение, изменение и удаление основных объектов.
    

### 9. Что необходимо сдать

## Тема 2. Сервис бронирования отелей

_Предметные требования к семестровому проекту_

> **Главный результат.** Приложение должно хранить отели и номера, искать свободные номера на выбранные даты и создавать бронирования.

Требования темы применяются вместе с разделом [«Общие требования»](#common).

### 1. Обязательная предметная модель

- **Hotel:** отель, название, город и адрес.
    
- **RoomType:** тип номера, например стандартный или семейный.
    
- **Room:** конкретный номер, вместимость, цена за ночь и тип.
    
- **Client:** клиент, оформляющий бронирование.
    
- **Booking:** номер, клиент, даты проживания, количество гостей, стоимость и статус.
    

**Дополнительные объекты.** Guest, Review, Address и Amenity можно реализовать дополнительно.

### 2. Минимальные связи между объектами

- Hotel содержит несколько Room;
    
- Room относится к одному RoomType;
    
- Client может иметь несколько Booking;
    
- Room может участвовать в нескольких Booking с непересекающимися датами.
    

### 3. Состояния объектов

Для состояний рекомендуется использовать enum. Переходы должны проверяться в бизнес-логике.

```text
CREATED → CONFIRMED → COMPLETED
    ↓          ↓
CANCELLED  CANCELLED
```

### 4. Основные сценарии

1. Создать отель, типы номеров и конкретные номера.
    
2. Найти номера по цене и вместимости.
    
3. Найти свободные номера на заданные даты.
    
4. Создать и подтвердить бронирование.
    
5. Отменить допустимое бронирование.
    
6. Получить статистику бронирований.
    

### 5. Обязательное REST API

Названия URL могут быть изменены, если сохраняются все перечисленные операции, входные данные и результаты.

|   |   |   |
|---|---|---|
|Метод и адрес|Принимает|Возвращает|
|GET /api/hotels|city или часть name|Список отелей|
|GET /api/hotels/{id}|ID отеля|Отель с основной информацией|
|POST /api/hotels|Название, город, адрес|Созданный отель|
|PUT /api/hotels/{id}|Новые данные|Изменённый отель|
|DELETE /api/hotels/{id}|ID отеля|Пустой ответ|
|GET /api/hotels/{id}/rooms|capacity, minPrice, maxPrice|Список номеров|
|POST /api/hotels/{id}/rooms|number, roomTypeId, capacity, pricePerNight|Созданный номер|
|PUT /api/rooms/{id}|Новые данные номера|Изменённый номер|
|GET /api/rooms/available|hotelId, checkIn, checkOut, guestCount|Только свободные подходящие номера|
|POST /api/bookings|clientId, roomId, даты, guestCount|Созданное бронирование|
|GET /api/bookings/{id}|ID бронирования|Бронирование и рассчитанную стоимость|
|GET /api/bookings|clientId, hotelId, status|Список бронирований|
|POST /api/bookings/{id}/confirm|ID бронирования|Подтверждённое бронирование|
|POST /api/bookings/{id}/cancel|ID бронирования|Отменённое бронирование|
|GET /api/bookings/statistics|hotelId или период|Количество бронирований и сумму|

### 6. Пример входных и выходных данных

#### Пример запроса

```json
{
  "clientId": 12,
  "roomId": 34,
  "checkIn": "2026-09-10",
  "checkOut": "2026-09-15",
  "guestCount": 2
}
```

#### Пример ответа

```json
{
  "bookingId": 81,
  "nights": 5,
  "pricePerNight": 4200,
  "total": 21000,
  "status": "CREATED"
}
```

### 7. Обязательные бизнес-правила

- Дата выезда должна быть позже даты заезда.
    
- Даты бронирования не могут находиться в прошлом.
    
- Количество гостей должно быть положительным и не превышать вместимость номера.
    
- Один номер нельзя забронировать на пересекающиеся даты.
    
- Стоимость рассчитывается как количество ночей, умноженное на цену за ночь.
    
- Цена за ночь фиксируется в бронировании.
    
- Отменённое бронирование нельзя подтвердить.
    
- Завершённое бронирование нельзя отменить или изменить.
    

### 8. Методы предметной области

Названия методов могут отличаться. Важно, чтобы изменение состояния выполнялось через понятные методы, а не только через набор сеттеров.

```java
room.canAccommodate(guestCount);
booking.overlaps(checkIn, checkOut);
booking.calculateTotal();
booking.confirm();
booking.cancel();
```

### 9. Исключения

Необходимо реализовать собственные исключения для основных ошибочных сценариев. Допускается объединить близкие ошибки в одно общее исключение.

- HotelNotFoundException;
    
- RoomNotFoundException;
    
- RoomNotAvailableException;
    
- InvalidBookingDatesException;
    
- RoomCapacityExceededException;
    
- InvalidBookingStateException.
    

### 10. Задания на Stream API и Optional

В проекте необходимо показать не менее четырёх операций из списка, включая группировку или агрегирование:

- отфильтровать номера по вместимости и цене;
    
- отсортировать номера по цене;
    
- найти самый дешёвый свободный номер;
    
- найти бронирование через Optional;
    
- сгруппировать бронирования по статусу или типу номера;
    
- вычислить общую стоимость бронирований отеля.
    

### 11. Хранение данных

- На промежуточном этапе данные хранятся в List, Set или Map.
    
- На итоговом этапе основные объекты становятся JPA-сущностями.
    
- Связи предметной модели должны быть отражены в базе данных.
    
- Репозитории реализуются через Spring Data JPA.
    
- После перезапуска приложения созданные данные должны сохраняться.
    

### 12. Критерии готовности темы

Проект по теме считается готовым, если вы можете последовательно показать:

- создать отель, тип номера, клиента и несколько номеров;
    
- найти свободные номера на указанные даты;
    
- создать бронирование и показать расчёт количества ночей и стоимости;
    
- подтвердить или отменить бронирование;
    
- загрузить бронирование из базы;
    
- показать ошибки пересечения дат и превышения вместимости;
    
- вывести группировку или сумму бронирований через Stream API.
    

> **На защите.** Объяснить назначение основных классов, распределение логики между Controller, Service и Repository, показывает данные в БД, один запрос со Stream API и минимум два ошибочных сценария.
